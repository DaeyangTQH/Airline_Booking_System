1. Hiện trạng dự án

Baseline: Maven reactor hiện build thành công. Tuy nhiên Booking Service chưa có test và mới chỉ là skeleton.
  • Đã có Spring Boot bootstrap class, POM và cấu hình ứng dụng.
  • Chưa có domain model, entity, repository, controller, migration hoặc test.
  • spring.application.name đang là payment-service, cần đổi thành booking-service.
  • POM dùng PostgreSQL driver nhưng Hibernate lại cấu hình SQL Server dialect.
  • Datasource URL và driver còn trống; thông tin đăng nhập đang hard-code.
  • Có cấu hình OpenFeign nhưng chưa có dependency OpenFeign.
  • ddl-auto: update chưa phù hợp để kiểm soát schema ổn định.
  • Chưa có cơ chế lấy current userId cho endpoint /bookings/me.
Đề xuất nền tảng: tiếp tục với SQL Server để phù hợp cấu hình hiện tại; dùng Flyway quản lý schema; dùng RestClient cho HTTP synchronous nếu nhóm chưa có chuẩn OpenFeign chung.

3. Kế hoạch code chi tiết

Giai đoạn 0 — Chốt contract và nền tảng

  • Thay PostgreSQL driver bằng Microsoft SQL Server JDBC.
  • Đưa URL, username và password sang biến môi trường.
  • Sửa tên ứng dụng thành booking-service.
  • Thêm Flyway; chuyển Hibernate sang ddl-auto: validate.
  • Giữ base package com.group3, đặt code trong com.group3.booking.
  • Chốt contract với Flying Search, Payment và API Gateway.

Đầu ra: ứng dụng khởi động được với database, migration chạy thành công và cấu hình dev/test tách biệt.

Giai đoạn 1 — Domain thuần và unit test

Tạo các enum:

  • BookingStatus, TicketStatus, FareClass
  • AddonType, AddonStatus

Tạo các value object:

  • BookingReference, TicketNumber
  • TicketQuantity, Money, ContactInfo

Tạo aggregate/entity và hành vi:

Unit test phải bao phủ đầy đủ BR-01 đến BR-14 trong tài liệu thiết kế.

Giai đoạn 2 — Database và persistence

  • Tạo migration cho bookings, booking_passengers, tickets, booking_addons.
  • Thêm foreign key nội bộ service và các index được đề xuất.
  • Thêm unique constraint cho booking_ref, ticket_number và tickets.booking_passenger_id.
  • Ánh xạ UUID thành UNIQUEIDENTIFIER, thời gian thành DATETIMEOFFSET.
  • Chuẩn hóa tên timestamp thành created_at và updated_at.
  • Tạo JPA entities, Spring Data repositories, persistence adapters và mapper.

Giai đoạn 3 — API nền tảng

  • Tạo request/response DTO và Jakarta Validation.
  • Tạo GlobalExceptionHandler và error response chuẩn.
  • Tạo generator cho booking reference và ticket number.
  • Cấu hình OpenAPI/Swagger.
  • Kiểm tra ownership: booking phải thuộc current user.

Giai đoạn 4 — Create Booking

POST /api/v1/bookings
  1. Lấy userId từ security context hoặc header nội bộ đáng tin cậy.
  2. Gọi FlightSearchPort để kiểm tra flight.
  3. Kiểm tra fare class và availability.
  4. Lấy giá từ Flying Search, backend tự tính tổng tiền.
  5. Tạo booking trạng thái PENDING và thời điểm hết hạn.
  6. Lưu snapshot giá; không truy vấn lại giá khi xem lịch sử.

External call nên chạy ngoài DB transaction. Có thể tạo adapter giả cho profile local nếu Flying Search chưa sẵn sàng.

Giai đoạn 5 — Passenger và Ticket trong một transaction

POST /api/v1/bookings/{bookingId}/passengers
PUT  /api/v1/bookings/{bookingId}/passengers/{passengerId}
load booking with lock
→ kiểm tra CONFIRMED
→ kiểm tra số passenger
→ tạo passenger
→ sinh ticket number
→ tạo ticket
→ commit

Dùng optimistic locking với @Version hoặc pessimistic lock để ngăn hai request đồng thời vượt quá ticket_quantity.

Giai đoạn 6 — Payment

POST /api/v1/bookings/{bookingId}/payment
POST /internal/v1/bookings/{bookingId}/payment-result
  • Xác thực callback từ Payment Service.
  • Cho phép callback SUCCESS lặp lại mà không tạo side effect mới.
  • Không cho phép CANCELLED → CONFIRMED.
  • Kiểm tra amount và currency trong callback.
  • Không giữ DB transaction trong lúc gọi Payment Service.
  • Bổ sung payment_id hoặc bảng liên kết payment để theo dõi giao dịch.

Giai đoạn 7 — Expiration và cancellation

find PENDING bookings where expires_at <= now
→ cancel theo batch
  • Dùng conditional update hoặc locking để nhiều instance không xử lý trùng.
  • MVP: cho phép cancel trực tiếp khi PENDING.
  • Tạm khóa cancel CONFIRMED cho đến khi có refund policy.
  • Expiration chỉ tác động đến booking PENDING.

Giai đoạn 8 — Add-on

POST   /api/v1/passengers/{passengerId}/addons
GET    /api/v1/passengers/{passengerId}/addons
DELETE /api/v1/passengers/{passengerId}/addons/{addonId}
  • Add-on chỉ được tạo cho passenger tồn tại.
  • Giá lấy từ catalog/backend, không nhận giá từ client.
  • Nếu chưa có payment riêng, dùng trạng thái đơn giản ACTIVE/CANCELLED.

Giai đoạn 9 — Seat integration

PUT    /api/v1/tickets/{ticketId}/seat
DELETE /api/v1/tickets/{ticketId}/seat
  1. Tìm ticket và đi qua passenger/booking để lấy flightId.
  2. Xác thực ticket có trạng thái ISSUED.
  3. Gọi Flying Search để validate và assign seat atomically.
  4. Cập nhật ticket trong Booking Service.
  5. Nếu cập nhật DB thất bại sau external assignment, gọi release để compensation.
Khi đổi ghế, nên có một endpoint atomic change-seat ở Flying Search. Hai thao tác release rồi assign riêng biệt có thể làm người dùng mất ghế cũ mà không nhận được ghế mới.

4. Khoảng trống nghiệp vụ cần chốt

Rủi ro overbooking: tài liệu mới yêu cầu kiểm tra availability, chưa yêu cầu giữ inventory. Hai booking đồng thời có thể cùng thấy còn vé và đều được tạo.

Giải pháp tốt nhất là Flying Search cung cấp:

  • hold inventory khi tạo booking.
  • confirm hold khi thanh toán thành công.
  • release hold khi booking hết hạn hoặc bị hủy.

Các quyết định còn lại:

  • Thời gian hết hạn booking, đề xuất mặc định 15 phút.
  • Số ticket tối đa trong một booking.
  • Chính sách cancel booking đã thanh toán.
  • Nguồn giá add-on.
  • Format booking reference và ticket number.
  • Cách API Gateway truyền current user.
  • Cách xác thực request nội bộ và payment callback.
  • Có giữ inventory theo quantity hay chỉ validate cho demo.

6. Definition of Done cho mỗi use case

  • Business rule được đặt trong domain/application layer, không nằm rải rác ở controller.
  • Request có bean validation và domain validation.
  • Error code và HTTP status đúng tài liệu.
  • Transaction boundary rõ ràng; không giữ transaction khi gọi service ngoài.
  • Có unit test cho happy path và state transition sai.
  • Có integration test cho repository/controller và external adapter.
  • Kiểm tra ownership theo current user.
  • Log có bookingId, bookingRef và correlation ID.
  • OpenAPI được cập nhật cùng endpoint.
  • mvn test chạy xanh từ root project.
